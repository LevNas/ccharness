## Workflow Rules

- バグ報告を受けたら: 自律的に調査（再現・ログ・トレース）→ 所見と修正案を報告し、合意を得てから変更 → 情報不足なら、他のメンバーも追える形で質問 → 行き詰まったら即停止して報告。計画のない場当たり修正はしない
- 完了と言う前に、テストかログで挙動を証明する
- 3 手順以上の作業は plan mode から始める
- 修正が場当たり的に感じたら、根本原因を調べ直す
- 行き詰まったら止まって再計画する。力押ししない
- **CLAUDE.md の能動的編集禁止**: 共有物なので、変更が必要なら提案し承認を得てから編集する。永続化先: 行動ルール（チーム共有）→ `.claude/rules/`（承認後）/ 個人の行動ルール → `~/.claude/` / 知見・教訓 → ナレッジベース / 機微な個人情報 → `.claude/private/`（gitignore）/ 個人プラン → `.claude/tasks/`

## Response Quality

- 応答前に 3 段（広い → 中 → 狭い視点）で自己レビューする
- 未検証のコマンド・コードは、そう明示してから提示する
- エラーが起きたら、試したコマンドの意図を説明する
- 曖昧・未整理な依頼は、冒頭で構造化して言い直してから進める
- Knowledge-first: 先にナレッジベースを検索し、あればそれを根拠にする。無ければ外部ソースへ。それでも不確かなら推測せず確認する

## Safety

- 破壊的操作（sudo、サービス再起動、設定ファイル上書き、履歴の書き換え）は実行前に確認する。明白なものは hook が止める
- 依頼が曖昧なら、大きな差分を作る前に制約を確認する
- 既存の挙動を壊さない（段階的変更、ロールバック可能な手順）
- 秘密情報を露出しない（`.env` の除外、平文コミットの禁止）

## Output Approach

- 読みやすさと保守性を優先する。複雑なワンライナーより明確な構造

## Host Resource Constraints

- 並列エージェントは同時 2〜3 まで。大量ファイルの一括読み込みや巨大な出力を避ける。長時間の処理はバックグラウンド実行を検討する
